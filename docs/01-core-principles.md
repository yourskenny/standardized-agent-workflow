# 核心原则

## 1. 智能体可靠性来自工程结构

不要把可靠性寄托在模型“足够聪明”上。一个可维护的智能体至少需要四个支柱：

- 面向检索整理过的知识库
- 明确的系统提示词和行为边界
- 可重复执行的发布流程
- 每次更新后的回归测试

模型能力重要，但它只是系统的一部分。

## 2. 原始资料不等于知识库

原始资料通常适合人阅读，不一定适合 RAG 检索。常见问题包括：

- 关键信息散落在长文档里。
- 问题和答案被切到不同片段。
- 标题很清楚，但正文缺少可独立理解的事实。
- 用户口语问法和正式字段不一致。

因此需要额外整理：

- 核心事实速查
- 关键事务问答核查表
- 同义词与意图映射
- 高风险事实表
- 用户不可见的维护清单

## 3. 问题和答案应尽量在同一检索片段中

高频事实建议使用“原子事实”写法：

```markdown
问：用户可能怎么问？
答：明确答案是什么？来源是什么？是否有边界？
```

避免一个标题下面隔很多段才出现答案。模型检索到问题但没有检索到答案时，很容易开始猜。

## 4. 区分没有资料和检索失败

测试时必须区分：

- 知识库确实没有答案。
- 知识库有答案，但检索或提示词没有让它答出来。

前者应让智能体明确说没有找到依据。后者应修复知识库切片、提示词、上传清单或平台配置。

## 5. 高风险问题必须保守

以下类型问题必须有明确来源，不能猜：

- 时间、地点、截止日期
- 费用、价格、评分、资格
- 法律、医疗、财务、安全
- 提交格式、迟交政策、许可条件
- 个人隐私、内部流程、权限边界

没有依据时，推荐回答：

```text
根据目前知识库资料，我没有找到关于这个问题的明确说明。建议向负责人确认。
```

## 6. 本地源文件不等于线上生效配置

很多平台中，本地文件只是源文件。真正生效的是平台中的：

- 应用系统提示词
- 绑定的知识库
- 已完成索引的文件
- 发布后的 Web App 或 API 配置

每次修改后都要确认同步、索引、绑定、发布和新会话测试。

## 7. 上传成功不等于回答正确

至少要检查六层：

1. 文件上传成功。
2. 文档索引成功。
3. 应用绑定正确知识库。
4. 对话实际触发检索。
5. 检索结果包含正确片段。
6. 模型根据片段生成正确答案。

任何一层出问题，最终回答都可能错。
