# 知识库设计

## 目标

知识库不是资料仓库，而是智能体的事实基础。它需要让检索系统和模型稳定找到答案。

## 推荐文件类型

### 1. 核心事实速查

用于保存最关键、最高频、最容易出错的事实。

适合内容：

- 时间、地点、负责人、联系方式
- 当前版本、当前政策、当前规则
- 评分、费用、资格、截止日期
- 已知不存在的信息

### 2. 关键事务问答核查表

用于覆盖用户最常问的问题。

推荐格式：

```markdown
## 问题：用户可能怎么问？

答案：直接回答。

依据：资料来源。

边界：不能推断什么；没有资料时怎么说。
```

### 3. 同义词与意图映射

用于把用户口语表达映射到正式字段。

示例：

```markdown
- “ddl / deadline / 什么时候交” = 截止时间或提交时间
- “怎么算分 / 成绩怎么算” = 评分方式
- “找谁问 / 联系谁” = 负责人或联系方式
```

### 4. 领域学习资料

用于解释专业知识、方法、工具和示例。

这类资料风险较低，但仍应说明来源和适用范围。

### 5. 边界与政策

用于告诉智能体什么不能做。

示例：

- 不能代写完整提交件。
- 不能编造没有依据的政策。
- 不能将个人作品当作公共资料。
- 不能把示例格式推断为正式提交格式。

### 6. 入库前抽象材料

用于处理“有价值但不适合直接上传”的资料。

适合内容：

- 历史作品、内部案例、会议纪要、访谈材料、项目复盘。
- 需要先脱敏、抽象或审核的资料。
- 可沉淀为规范、方法论、检查清单或主题地图的材料。

处理原则：

- 原始资料和逐份摘要保存在 `_pre_ingestion/`，默认不上传。
- 只有抽象、审核后的方法论条目才进入正式知识库目录。
- 上传后必须同步更新智能体行为协议和测试问题。

详细流程见 [07-pre-ingestion-abstraction-workflow.md](07-pre-ingestion-abstraction-workflow.md)。

## 元信息规范

建议每个知识文件开头加入 YAML 元信息：

```yaml
---
kb_type: course_fact
domain: course
version: 2026-spring
source: syllabus
risk_level: high
update_frequency: every_semester
owner: teacher
last_checked: 2026-05-02
upload_to_agent_kb: true
---
```

字段说明：

- `kb_type`：资料类型，例如 `core_fact`、`faq_table`、`intent_map`、`policy`、`learning_material`。
- `domain`：领域，例如 `course`、`hr`、`product`、`research`。
- `version`：适用版本、学期或业务周期。
- `source`：资料来源。
- `risk_level`：`high`、`medium`、`low`。
- `update_frequency`：`every_cycle`、`when_changed`、`rarely`。
- `owner`：维护责任人。
- `last_checked`：最近核查日期。
- `upload_to_agent_kb`：是否上传到智能体知识库。

## 风险分级

### High

答错会造成明显损失、误导或合规风险。

要求：

- 必须有明确来源。
- 系统提示词中应强调保守回答。
- 回归测试必须覆盖。

### Medium

答错会影响体验或学习质量，但通常可纠正。

要求：

- 尽量有来源。
- 可以给出解释和适用条件。

### Low

通用解释、背景知识、示例代码等。

要求：

- 可以使用通用知识，但要避免与项目资料冲突。

## 知识库更新原则

- 一个文件尽量只处理一个主题。
- 高频事实短句化。
- 问法和答案尽量放在同一片段。
- 不上传维护资料。
- 不上传入库前处理区、原始资料或逐份摘要。
- 不上传个人隐私或用户个人作品。
- 过期内容归档，不和当前内容混传。
